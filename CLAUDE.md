# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BrowserX (npm package `browserx`, formerly "Claude Browser") is an Electron desktop app: a Claude Code chat pane on the left, a real embedded browser on the right, which the agent controls directly (screenshots, clicks, JS eval, CDP) via the `@anthropic-ai/claude-agent-sdk`. It also ships a purpose-built tool set for publishing articles to WeChat Official Accounts (公众号) through that same browser view.

## Commands

```
npm start            # run the app (electron .)
npm run debug         # electron . --remote-debugging-port=9334 (works in cmd.exe too; CB_DEBUG_PORT still works), for driving the renderer over CDP from outside
APPLE_KEYCHAIN_PROFILE=browserx-notary npx electron-builder --mac   # → dist/BrowserX-<version>-arm64.dmg, signed + notarized (no npm script wraps this)
npx electron-builder --win --x64 --publish never                    # → dist/BrowserX-Setup-<version>-x64.exe (NSIS, unsigned); needs build/win-git, see Windows notes
```

**Windows notes:**
- The installer bundles a Git for Windows tree from `build/win-git` as `resources/git` (gitignored). Claude Code on Windows runs its Bash tool through Git Bash, so `gitBash()` looks there first, then `build/win-git`, `CLAUDE_CODE_GIT_BASH_PATH` and the usual Git install folders, and `claudeEnv()` passes the result as `CLAUDE_CODE_GIT_BASH_PATH`. CI (`.github/workflows/windows.yml`, manual or a `win-v*` tag) downloads the official PortableGit. For a local build, copying an installed `C:\Program Files\Git` into `build/win-git` works too.
- `CB_SMOKE=1` (optionally `CB_SMOKE_OUT=<file>`) makes the app check that it can run `claude.exe --version`, Git Bash and `safeStorage`, write the result as JSON and exit. CI runs it on `dist/win-unpacked`.
- User data is `%APPDATA%\BrowserX`. `safeStorage` uses DPAPI there instead of the keychain. `shell.trashItem` goes to the Recycle Bin.
- No auto-update on Windows: `updater.enabled` is Mac-only, so 检查更新… only compares versions. It asks `/api/desktop/version?platform=<platform>-<arch>` and opens the returned `url` (only if it is on the portal, else `<portal>/download`).
- **Portal side (added 2026-11-05, edited directly on the server, not committed; backup and patch in `~/bak/browserx-windows-20261105-152500/` on the server):** `BROWSERX_WINDOWS_FILE` in the portal `.env` names the installer in `storage/app/private/downloads/`, and `BROWSERX_WINDOWS_VERSION` defaults to `BROWSERX_VERSION`. With it set, `/download` serves the `.exe` to browsers whose User-Agent contains `Windows` and the dmg to everyone else. `/download/mac` and `/download/windows` pick explicitly. The version API returns the Windows version and `/download/windows` for `platform=win32…`. The home page and the member panel show both downloads. Without it everything behaves as before. Windows release: build, upload the exe to `storage/app/private/downloads/`, then set `BROWSERX_WINDOWS_FILE` (and `BROWSERX_WINDOWS_VERSION` if it differs from the Mac version).
- Platform wording: the renderer uses `IS_MAC` / `MOD` / `FINDER` / `TRASH` (Ctrl+, 文件资源管理器, 回收站 on Windows). Locale keys carry a `{0}` for these, as in `关闭标签（{0}W）`. `help.js` rewrites the help page on non-Mac at load: `⌘` → Ctrl, and the two `~/Library/Application Support/BrowserX/…` paragraphs become File Explorer + `%APPDATA%\BrowserX\…` with a per-language phrase. The help HTML files themselves stay Mac-worded.
- `protectToolFiles()` compares paths case-insensitively (Windows and default APFS). It also accepts Git Bash `/c/…` paths for Edit/Write. For Bash and PowerShell commands it matches only the last two segments `BrowserX/tools/` with either separator, so `~`, `$HOME`, `%APPDATA%` and `$env:APPDATA` forms are all caught. `BASH_WRITE` includes cmd and PowerShell write commands.
- Session paths under `~/.claude/projects/` use Claude Code's rule, every non-alphanumeric character → `-`, so `C:\Users\x\BrowserX` becomes `C--Users-x-BrowserX`.

There is no lint config and no test suite in this package.

**Packaging notes:**
- Signed with the Developer ID Application certificate `EVERGREEN FAMILY OFFICE LIMITED (77L5U5LVW4)` from the keychain (`mac.identity`; the owner approved this), with hardened runtime and `build/entitlements.mac.plist` (JIT, unsigned executable memory, disabled library validation, which V8 and the bundled `claude` need). electron-builder signs nested binaries, including `claude`, with the same entitlements. Verified that the signed app launches, spawns `claude` and chats through the relay.
- Notarization (`mac.notarize: true`) reads credentials stored once with `xcrun notarytool store-credentials browserx-notary --apple-id … --team-id 77L5U5LVW4`, passed in through `APPLE_KEYCHAIN_PROFILE`. Without that env var electron-builder silently skips notarization, and Gatekeeper then rejects the app as "Unnotarized Developer ID".
- With `mac.identity: null`, `scripts/after-pack.js` falls back to ad-hoc signing (bundled `claude` first, then the whole `.app`); it does nothing when an identity is set. Don't use identity `"-"`: electron-builder treats it as a name lookup, skips signing and leaves a broken signature.
- Electron 45 (Chromium 156, Node 24). `@anthropic-ai/claude-agent-sdk` is pinned to an exact version: it bundles the `claude` binary, so pinning keeps builds reproducible. Electron 45 deprecates the sync `safeStorage` calls (`isEncryptionAvailable` / `decryptString`), which still work for now.
- **Auto-update** (`updater.js`, **electron-updater 6.8.11** with differential download, packaged macOS builds only; Windows not yet). The feed is the generic provider `<portal>/updates/` (`build.publish`, which also writes `app-update.yml` with `updaterCacheDirName: browserx-updater`). nginx serves `storage/app/updates/` there: `latest-mac.yml` (version, zip URL, sha512, size), the zip and its `.zip.blockmap`. The app checks 30 s after start and every 4 h, downloads in the background, then asks to restart (`quitAndInstall`, falling back to install on quit). The final install is still Squirrel.Mac, served the zip through electron-updater's local proxy, so old and new builds must be signed with the same Developer ID. **Differential:** it compares the new blockmap with the previous version's and fetches only changed blocks with multi-range requests (nginx answers `206 multipart/byteranges`). That needs the previous `update.zip` in `~/Library/Caches/browserx-updater/`, which electron-updater keeps after each download, and the previous blockmap, from its cache or the feed dir. So the first update through electron-updater (fresh dmg install, or coming from 0.1.8) is a full download, and later ones are diffs. Measured 2026-11-06 with two Developer-ID-signed builds (9.0.0 → 9.0.1, a few changed lines): `Full: 249,751 KB, To download: 2,614 KB (1%)`, then the app installed and relaunched as 9.0.1 with a valid signature and its fuses intact. Logs: `<userData>/logs/updater.log`. 0.1.8 and older use Electron's built-in autoUpdater against `/api/desktop/update/darwin-arm64`, which the portal keeps serving so they can make one full update onto electron-updater. 检查更新… calls `updater.menuCheck()`: electron-updater in packaged builds, a plain version compare against `/api/desktop/version` in dev. Test hooks: `CB_UPDATE_FEED` overrides the feed dir; `CB_UPDATE_TEST=install|quit` skips the dialog after download.
- Release: bump `version`, build with `APPLE_KEYCHAIN_PROFILE … npx electron-builder --mac --publish never`. Upload the dmg to `downloads/`, and the zip, `.zip.blockmap` **and `latest-mac.yml` (last, once the zip is in place)** to `updates/`. **Keep the previous version's `.zip.blockmap`** (and zip) in `updates/`, because clients diff against it. Then set `BROWSERX_VERSION`, `BROWSERX_DOWNLOAD_FILE` and `BROWSERX_UPDATE_FILE` in the portal `.env` (old clients still use those). `build.files` excludes `android/**`: after the Android merge it had added 84 MB to `app.asar`. `electronLanguages` keeps 8 app locales; it doesn't trim the Chromium framework's 220 `.lproj` (about 9 MB).
- **Customers can extend BrowserX only through plugins, not change the app itself** (user rule, 2026-11-06). Four layers:
  1. **Electron Fuses** (`scripts/after-pack.js` → `flipFuses`, using `@electron/fuses` 1.8.0, because electron-builder 25 has no `electronFuses` option). Flipped before signing: RunAsNode, NODE_OPTIONS and `--inspect` off, OnlyLoadAppFromAsar on, and on macOS EnableEmbeddedAsarIntegrityValidation on (electron-builder writes `ElectronAsarIntegrity` into Info.plist). Windows keeps asar integrity off, since electron-builder 25 doesn't embed the Windows integrity resource and the app wouldn't start. Cookie encryption is left alone, because changing it would drop every saved login. Verified on a local `--dir` build: the self-check (`CB_SMOKE`) passes; an `app.asar` repacked with one changed line dies with `Integrity check failed for asar archive entry '<header>'`; `ELECTRON_RUN_AS_NODE=1 … -e` and `NODE_OPTIONS=--require` run nothing. Plugins aren't affected, because they live in `<userData>/tools/`, not in the asar.
  2. **The `protectToolFiles` hook also covers the app itself.** `main.js` `PROTECTED_PATHS()` lists the internal data files (`config.json`, `market-installed.json`, `tool-keys.json`, `tool-creds.json`, `schedules.json`) and, in packaged builds, the install dir (`BrowserX.app` / the Windows install folder). Edit/Write into them, and Bash/PowerShell writes that name them, `app.asar` or `BrowserX.app`, or `asar extract/pack`, are denied with a "make it a plugin" message. Reads stay allowed, and so do `_drafts/`, the work folder and plugins' own files such as `prudential_login.json`. Tested with 19 commands. Like the tools-dir check, it's a heuristic.
  3. Packaged builds drop 显示 → 界面开发者工具 (the left UI's DevTools can call any IPC). 网页开发者工具 stays for plugin making.
  4. `BROWSER_PROMPT` tells Claude not to modify BrowserX and to offer a plugin instead. User Claude settings are still loaded (`settingSources` includes `user`), because plugin making relies on the user's skills; the hook can't be turned off by those settings.
  Money and permission rules stay on the portal (quota in the relay, membership and purchase checks on download), so a modified client can't bypass them anyway.
- `scripts/dev-app-name.js` (prestart) renames the dev `Electron.app` in Info.plist, which breaks its signature. With a broken signature macOS can't remember "Always Allow" for the `BrowserX Safe Storage` keychain item and prompts on every launch, so the script re-signs ad-hoc whenever it edits the plist or finds the signature invalid.
- electron-builder nests the platform package under `claude-agent-sdk/node_modules/`. The `asarUnpack` glob therefore has to be `**/node_modules/@anthropic-ai/claude-agent-sdk-*/**`, and `nativeClaude()` checks both the top-level and the nested location.
- The build needs about 1.3 GB of free disk space at peak.

## Architecture

**Process split (standard Electron, but with a twist):** `main.js` creates one `BrowserWindow` (the whole UI, `index.html`/`renderer.js`) and layers `WebContentsView`s into it — those views *are* the right-hand "browser". `renderer.js` never touches a view directly; it only resizes them by sending the DOM position of `#stage` through the `bounds` IPC call so the native views line up under the DOM layout. `preload.js` exposes exactly two bridge calls: `api.call(channel, ...args)` → `ipcRenderer.invoke` and `api.on(channel, fn)`.

**Tabs (left tab = one chat = one `Agent`, owning one or more web pages):** `main.js` keeps `tabs` (`Map<id, {pages, page, agent}>`, `t.view` is a getter for the active page's view) and `cur`. `createTab()` builds the `Agent` first, then its first page with `addPage()`. A background chat's agent never touches the visible page. **Web pages (right-hand strip, `#pagebar`, shown when a chat has 2+ pages):** a site's `window.open` / `target=_blank` goes through `setWindowOpenHandler` → `createWindow`, which adopts the new guest `webContents` into a `WebContentsView` (`opener` and `postMessage` survive same-origin; cross-origin COOP sites sever them, like Chrome) and makes it the active page. Past `MAX_PAGES` (10) the link loads in the current page. **A new page is activated only after it survives 400 ms** (`createWindow` adds it with `activate: false`, then `activatePage` + `pageOpened`). 永明's login page runs `window.open('','iws',''); a.close()`; switching immediately made the active page one that was destroyed a moment later, so tools failed with "Object has been destroyed". Closing a page returns to its `opener` page when that is still open. `Agent.js()` also retries once on the current page when the page it started on was destroyed mid-call. A page that calls `window.close()` is removed on `destroyed`. The agent reads `this.wc` through `ctx.getWc()`, so every browser tool, `WeChat` and the custom-tool `ctx` act on the **active page**. `doClick` / `doPress` capture `wc` at the start, so a click that opens a tab doesn't send mouse-up to the new page. The model gets `tab_list` / `tab_new` / `tab_switch` / `tab_close` (1-based indexes) and custom tools get `ctx.tabs` (`list/open/switch/close/waitForNew`). When a site opens a page during a model turn, `Agent.pageOpened()` queues a note that the next browser-tool result appends. Notes are only queued while `running` and cleared on each `send()`, otherwise pages opened by hand would surface much later. `Recorder` attaches each page separately (`attach` / `addPage`, `cdp(method, params, wc)`): pages opened while recording are recorded too, with entries tagged `tab: n` once there's more than one, and closing one recorded page doesn't stop the recording. Making mode's fresh start closes extra pages (`ctx.pages.reset()`). Inactive views are hidden with `setVisible(false)` and created with `backgroundThrottling: false` — verified that a hidden view still returns fresh `capturePage()` images, runs timers and accepts `sendInputEvent`, so background agents work normally. All views get the same bounds (a 0-size `bounds` call while dragging the splitter only hides the current one). Agent events are sent as `{...ev, tab: id}`; IPC calls that act on a conversation (`agent:*`, `tools:run`/`tools:stop`, `history:resume`) take a trailing tab id, falling back to `cur`. Nav, recording buttons, history list and toolbox listing act on `cur`. Tool-making mode is limited to one tab at a time (`ctx.otherMaking`), and `making:*` banner calls go to that tab; after a tool is finished or imported, `ctx.toolsChanged` reloads custom tools in the other tabs' live sessions. `wechat.js` serializes clipboard-write + paste through a module-level `clipLock`, since the OS clipboard is shared. In `renderer.js` each tab has its own state object (`tabState`: message container, card maps, running, making…); the visible container gets `id="msgs"` (all chat CSS targets `#msgs`). `cur` is the shown tab and `T` the tab being rendered into — events from a background tab and async tool results use `inTab()` to temporarily point `T` (and therefore `add()`) at their own tab. Resuming a history session that is already open switches to that tab; otherwise it opens in a new tab unless the current one is empty. Shortcuts ⌘T / ⌘W / ⌘1…9 / ⌘⇧[ ] are also caught via each view's `before-input-event` and forwarded as `tabkey`, so they work while focus is in the web page. Max 8 tabs.

**BrowserX account (`account.js`, portal `browserx.xingke888.com` = `~/github/browserx-portal`):** login is a loopback + PKCE flow — `Account.login()` listens on a random `127.0.0.1` port, opens `<portal>/desktop/authorize?port&state&challenge&device` in the *system* browser (`shell.openExternal`), and on `/callback?code&state` exchanges `code + verifier` at `POST /api/desktop/token` for a Sanctum token; callbacks with the wrong `state` are ignored, the wait times out after 10 minutes, `account:cancel` aborts it. The token lives in `main.js`'s `accountToken`, **not** in `cfg` (cfg is sent whole to the renderer), and is written to `config.json` as `accountTokenEnc` only when `safeStorage` encryption is available. All other calls go to `/api/desktop/*` with `Bearer`; a 401 clears the token (logged out), 402/403 errors carry the site `url` (buy / become a member) which `handle()` passes through as `{error, url, needLogin}` so the renderer can show a "去网站看看" button (`.ac_link` → `account:open`, which only opens URLs on the portal). Market install = download code (`/market/{id}/download`) to a temp file, then the **same** `importPreview` → user confirm → `tools:importConfirm` path as a local import; successful market installs are recorded in `<userData>/market-installed.json` (name → id/version/sha256) for the "已安装 / 有新版本" labels. Publish (`market:publishInfo` / `market:publish`) posts the toolbox file plus form fields; the portal decides new tool vs. new version by the file's `name`, and everything goes to admin review. `CB_PORTAL` points at another portal (local testing) and `CB_ACCOUNT_TOKEN` injects a token without the browser step — test-only, like `CB_USER_DATA`.

**插件市场 header button (`#btnMarket`, right of 工具箱):** hidden by default and shown only when the portal admin turns on 系统设置 → 插件市场分成 → 在客户端显示「插件市场」按钮 (setting `market.show_client_button`). The renderer reads `portal:clientConfig` (main.js → public `GET /api/desktop/client-config` → `{show_market_button}`, no login) at start and every 30 min, and caches the last result in `localStorage` (`cb.showMarketButton`) so it survives offline starts. Clicking opens the toolbox on `renderMarket()`. The in-toolbox 插件市场 button and the account panel's entry are not affected by the switch.

**`browserx://install/<id>` links (website plugin detail page → 在 BrowserX 中安装):** the browser asks whether to open BrowserX, then `handleLink()` in `main.js` sends `marketLink` and the renderer's `installFromLink()` opens the toolbox and runs the same path as the market's 安装 button (`market:install` → `showImportPreview`, so nothing installs without the user confirming). Not logged in, no membership or an unbought paid tool stop on the market page with the reason. Only that exact URL shape is accepted. macOS delivers it through `open-url` (also on cold start, queued in `pendingLink` until the renderer asks `link:pending`); Windows starts a second process with the URL in argv, so win32 takes a single-instance lock and forwards it in `second-instance`. The app registers itself with `setAsDefaultProtocolClient` on every start, and `build.protocols` puts `CFBundleURLTypes` in the packaged Info.plist. In dev on macOS the registration points at `node_modules/electron/dist/Electron.app`, so the link only works while `npm start` is running, and the last-started app (dev or packaged) owns the scheme.

**Claude credentials / portal relay:** `Agent.claudeEnv()` decides how the bundled `claude` authenticates, for both chat sessions and `askModel()`. If the user filled their own API Key in settings, that key (plus optional `baseUrl`) is used. Otherwise a BrowserX account login is required: `ANTHROPIC_BASE_URL` points at `<portal>/api/desktop/claude` and `ANTHROPIC_AUTH_TOKEN` is the account token, which the CLI sends as `Authorization: Bearer`, the format Sanctum expects. The portal's `ClaudeRelayController` swaps in the real key from the server `.env` (`CLAUDE_UPSTREAM_*`) and streams the response back, so no Claude key ships with the app. Shell `ANTHROPIC_*` vars and a local Claude Code login are deliberately ignored, so they can't bypass the account. The CLI keeps retrying a 401 instead of failing, so `start()` and `askModel()` first call `ctx.checkAccount()` (`checkAccount()` in `main.js`). It wraps `account.refresh()`, which clears an expired login and throws "登录已失效". The result is reused for 60 s, because a tool can call `ctx.ask` several times in a row. On a network error it returns the last known state marked `stale`, and `checkQuota()` skips stale states, so the relay decides (402 if really over). An earlier version blocked users on a cached "已用完" that was no longer true after an admin reset or a new package, while a local proxy made the portal unreachable from Node. `Account.request` retries a GET once on a network error: a single `ECONNRESET` on `/me` once made a tool's `ctx.ask` fail. **Relay field stripping:** the first request of every claude process used to get two 400s before a 200. The gateway rejects `messages[].output_config` ("messages.1.output_config: Extra inputs are not permitted", carried by the mid-conversation `role: system` message) and `thinking.display: "updates"` (it only accepts summarized / omitted). The CLI drops one field per retry and remembers it for the rest of the process, so each first message cost two extra round trips, about 1.8 s. The portal relay now removes both fields before forwarding (`ClaudeRelayController::compatBody`; `CLAUDE_UPSTREAM_STRIP_NEW_FIELDS=false` turns it off for an upstream that supports them), so the first request succeeds. Measured through a local logging proxy: before, 400 (1.1 s), 400 (0.7 s), 200 (2.6 s), 4.7 s in total; after, a single 200 and 3.7 s. **Root cause, fixed on the gateway (2026-11-04):** tokens.xingke888.com wasn't forwarding the client's `anthropic-beta` header to the official API, so `per-turn-control-2026-07-01` and `thinking-display-updates-2026-08-18` never took effect. Proof: a made-up beta value returned 200 instead of the API's "Unexpected value(s) … for the anthropic-beta header". After the gateway fix, that made-up value gets the official 400, and both fields return 200 with their betas (`output_config` is only allowed on `role: system` messages, which is where Claude Code puts it). Terminal Claude Code connecting straight to the gateway had the same first-request 400 and is fixed too. The portal now runs with `CLAUDE_UPSTREAM_STRIP_NEW_FIELDS=false` (backup `.env.bak-*` on the server), so both fields pass through. Measured: a single 200 on every first message, 2.9–3.8 s, no thinking blocks for a trivial prompt. One earlier run took 20 s and didn't recur. The code default stays `true`, as a safety net for a gateway that drops betas. What remains is upstream latency: about 1.4–2.7 s from the portal server straight to the gateway, even for a tiny prompt. Each request carries about 34k tokens (52 tools ≈ 52 KB, system ≈ 11 KB, 90 KB body), cache-read after the first. The gateway also answers every model id as `claude-opus-5-5`. Logging in or out resets live sessions that don't use a user key. Packaged builds hide the settings button and the 设置… (⌘,) menu item (`SHOW_SETTINGS = !app.isPackaged || CB_SETTINGS=1` in `main.js`, read by the renderer via `app:showSettings`). Customers only need the account login, while `npm start` keeps settings. `button.icon` is `display:grid`, so the renderer hides the button with `style.display`, because the `hidden` attribute would not take effect.

**Browser identity (anti-bot):** some sites (Akamai-fronted, e.g. 永明) block Electron's default User-Agent because it contains `Electron/x` and `BrowserX/x`. `useChromeIdentity()` in `main.js` strips those tokens on the `persist:browser` session. Overriding the UA string makes Chromium stop sending `sec-ch-ua*` client hints, so two things put them back. `Agent.applyIdentity()` sets `Emulation.setUserAgentOverride` with Chrome brand metadata (Google Chrome / Chromium, full version, macOS + real `platformVersion`, arm) on every page; this covers `navigator.userAgentData` and subresource or `fetch` requests, and is re-applied when `cdp()` re-attaches. A `webRequest.onBeforeSendHeaders` hook adds the three default hints (`sec-ch-ua`, `-mobile`, `-platform`) to https main and sub frames when they're missing, because navigations, both `loadURL` and in-page, don't get them from the CDP override. Verified with postman-echo: all three request kinds match real Chrome, and `navigator.webdriver` is false.

**Language / UI translation (`i18n.js`, `locales/`):** one setting (`cfg.replyLang`, menu BrowserX → 语言, or settings) drives both Claude's reply language (`LANG_PROMPT(lang)`, re-announced on the next message when it changes mid-session) and the UI. `system` resolves from macOS preferred languages: zh-Hant/TW/HK/MO → zh-TW, other zh → zh-CN, ja/ko/fr/de/es → themselves, anything else → en. Simplified Chinese is the source text, and `locales/<lang>.json` maps that Chinese source to the translation, with `{0}`… for interpolated parts. The main process uses `L(key, vals)` for native menus and `updater.js` dialogs. The renderer doesn't call `t()` everywhere: `BXI18N.domTranslator` translates every text node and `title` / `placeholder` / `aria-label` that appears (MutationObserver), remembers the Chinese original and retranslates on the `i18n` IPC event. Pattern keys capture interpolated parts and translate them recursively. It skips `.msg.ai, .msg.user, pre, code`. Text that's prefixed by a symbol or built inside CSS has to be translated explicitly with `TR()`: the banner steps (`renderMakingSteps`) and the empty-chat hint (`--empty-hint`). Big numbers use `Intl` compact notation (`fmtBig`), and `body.ui-latin` turns the round banner buttons into pills. Workflow: `node scripts/i18n-extract.js` collects keys from index.html, renderer.js, main/updater `L()` / `t()` and agent.js `MAKING_STEPS` into `locales/_keys.json`. Then `GW_KEY=… python3 -I scripts/i18n-translate.py` fills only missing or invalid entries (placeholder and Markdown checks, plus a curl User-Agent because Cloudflare 1010 blocks Python's). The extractor also scans agent.js, recorder.js, wechat.js, account.js, main.js, scheduler.js and toolcrypt.js for Chinese literals and templates (the notes, hints and errors that end up in the chat). It skips model-facing text: `*_PROMPT`, `REPLY_LANGS`, `BUILTIN_TOOLS`, `tool(…)`, `.describe(…)`, `send(…)`, `logMaking(…)`/`askModel(…)`/`userSend(…)` arguments, `rule`/`description`/`system` properties, and anything over 400 chars. Multi-line strings get one key per line too, because the making intro renders one `.nl` div per line. `tr()` falls back to stripping leading or trailing symbols and list numbers, and then to translating sentence by sentence (split on 。！？), for messages the program assembles from several literals. The help page is translated whole: `GW_KEY=… python3 -I scripts/i18n-help.py [lang…]` writes `locales/help/<lang>.html`, checking that tags and ids match the source and retrying up to 3 times because the gateway sometimes truncates long replies. Re-run it whenever help.html changes. `openHelp` / `helpFile()` picks the localized file (falling back to help.html), and `reloadHelp()` reopens an open help window when the language changes. `help.js` localizes the version label from `<html lang>`. **Quota errors carry a link:** `checkQuota` throws with `url` and `label` (充值 when the portal sent `urls.credit`, otherwise 开通会员 for non-members). `handle()` passes `label` through, and `errWithLink` renders it as a primary button. The portal only sends `urls.credit` while Claude credit is enabled, so the account panel's 充值 row hides itself when top-up is off.

**Downloads / uploads / JS dialogs (`main.js` `watchDownloads`, `Agent.uploadFiles` / `onDialog`):** downloads on the `persist:browser` session never show a save dialog. They go to `~/Downloads/BrowserX/` with a unique name, and the chat that started them gets `downloadStarted` / `downloadDone`: a note with a 在访达中显示 button (`downloads:show`, limited to that folder) plus a `pageNotes` entry for the model. The model has `downloads` and `upload_file` (CDP `DOM.setFileInputFiles` on `input[type=file]`, so no OS file picker), and custom tools have `ctx.downloads.list/waitFor` and `ctx.upload`. JS dialogs: `watchPage` enables the CDP `Page` domain on every page, and `cdp()` re-enables it after re-attaching. `Page.javascriptDialogOpening` is answered only while the model or a tool is running: alert → OK, confirm / beforeunload → OK unless `guard()` denies, with a note to the chat and the model. When the user is operating by hand, the native dialog is left alone (verified it still shows). Electron doesn't implement `window.prompt()`, so it throws regardless.

**Scheduled tool runs (`scheduler.js`):** tasks live in `<userData>/schedules.json` (`tool`, `args`, `mode` daily / weekdays / interval / once, `time`, `every` minutes, or `at` = local `YYYY-MM-DDTHH:mm` for once) and a 30 s tick runs the due ones. A one-time task must be set in the future, runs once when due (or on the next launch if the app was closed) and then disables itself; editing its `at` re-arms it. After 定时运行 is saved the toolbox jumps to the 定时任务 list. A daily task runs once today if its time has passed and it hasn't run yet, but only for times after `createdAt`, so a newly created task never fires immediately. `runScheduled()` in `main.js` runs the tool directly (`runCustomTool`, no model) in a background chat it creates and remembers (`schedTabId`). It emits `sched` events into that chat and shows a system `Notification` whose click switches to the chat. A busy chat or full tab bar throws `retry`, so the run is retried next tick instead of recorded. The renderer's `tabs` handler now calls `tabOf()` for unknown ids, so chats the main process opens also appear on the left. UI: the 定时运行 button on a tool's standard form (it reuses the same `collect()` as 运行) and the 定时任务 list in the toolbox. 修改 on a list item reopens `scheduleDialog(t, args, task)` with the schedule and the tool's params (drawn by `schedArgFields` from `paramsToFields`) and saves through `schedules:update`. Tools without `params`, such as `form()` pages, can only change the time there. Each run appends `{at, ms, ok, text}` to the task's `history` (newest first, last 50; `retry` runs aren't recorded). `list()` omits the history and sends `runs` / `okRuns` counts. The 执行情况 button loads it through `schedules:history` into a modal. `update()` sets `changedAt` when mode / time / every / args change, and `list()` sorts newest `changedAt || createdAt` first, so pausing or running a task doesn't move it.

**Claude quota (portal `ClaudeQuota`):** the relay counts each response's usage (`UsageMeter` reads SSE `message_start` / `message_delta` or the JSON `usage`) into `claude_usages`, one row per user per day. Billable = input + output + cache write + cache read / 10. Defaults are 2,000,000 per day for members and 200,000 for others. Over quota the relay answers 402 `billing_error`: Claude Code makes only one request and shows the message (429 retries forever, 400 retries 6 times, and 403 shows as an auth failure, all tested). `/api/desktop/me` includes `claude` {used, limit, exceeded}. The account panel shows a meter, and `Agent.checkQuota()` refuses to start a session when the quota is already used up. **One quota-exceeded message:** `checkQuota` throws `{quota: true}`, and a mid-session relay 402 arrives as an assistant message `API Error: 402 …` (followed by `m.error` 'unknown'), which `loop()` swallows and turns into a `quota` event, with `done` getting `quota: true` and no error. Both render `quotaHtml()` in renderer.js: one `<span>` per sentence so the DOM translator matches each, and buttons for 充值 (`urls.credit`), 用积分兑换 (`tokens_per_point` > 0, opens `openInvite`) and 开通会员 (non-members). The wording mirrors the portal's `ClaudeQuota::exceededMessage`, which old clients show verbatim, with a URL appended.

**Market tool updates (`checkToolUpdates` / `updateMarketTool` in `main.js`):** each tool version on the portal gets an internal `build` number, 1, 2, 3… per tool, assigned on upload. The developer's `version` string is only for display. `market-installed.json` records `build` at install. 40 s after start, every 4 h, and when the toolbox opens, the app posts `{id, build}` (or `version` for older records, which the portal maps to a build) to `/market/updates`. That returns tools whose current approved build is higher, with `can_install` / `reason` (membership expired, paid tool not bought). The toolbox shows 有新版本 x + 更新 on those cards, sorts them first and adds a 全部更新 bar. The 自动更新工具 checkbox (`cfg.autoUpdateTools`, default on) installs them silently through the same `importPreview` → `confirmImport({overwrite, quiet})` path. **A new version that adds a `scanRisks` category the installed code didn't have** (for example it starts reading files or cookies) is never auto-installed. It's marked `needsConfirm`, and 更新 then opens the normal install confirm page with 替换 pre-checked. A tool being edited in making mode isn't updated. **Market title + 官方 / 精品 badges:** a market-installed tool is listed under its portal title (`tools:list` prefers `market-installed.json`'s `title` over the code's `title`, which can differ, e.g. `wechat_publish` = 公众号写作发布 in code, 微信公众号发稿 on the portal). The toolbox also shows the market's 官方 (blue seal) and 精品 (gold star) badges (`officialBadge` / `featuredBadge` in `renderer.js`, shared with the market list) on tools installed from the market. `title` / `official` / `featured` are stored in `market-installed.json`, first from the download response and then from the `badges` array that `/market/updates` returns for every installed tool still visible on the portal. `syncToolBadges()` clears the badges (but keeps the title) for tools the portal no longer returns, writes the file only on a change, and sends `toolBadges`, on which the renderer re-reads `tools:list` (not `renderToolboxList`, which would trigger another update check) and redraws. An older portal without `badges` leaves the stored values alone.

**Market tool protection:** tools installed from the market that belong to someone else (`market-installed.json` entry without `mine`; the portal's download response says `mine`) are stored encrypted as `<tools>/<name>.bxt` (`toolcrypt.js`: AES-256-GCM, random key per tool, tool name as AAD, keys in `<userData>/tool-keys.json` encrypted with `safeStorage`). `loadToolFile` decrypts and compiles them in memory via `Module#_compile`, so no plaintext touches disk; `readCustomToolDefs` lists `.bxt` alongside `.js`. They can't be edited / exported / published (`isMarketTool` + a `.bxt` check in `startMaking` / `exportInfo`; the UI hides those buttons and shows a "市场" chip), their failure message tells the model not to look for the source, deleting one also drops its key, and on startup `encryptMarketTools()` converts older plaintext market installs (deleting the `.js` only after a decrypt round-trip matches). This raises the bar, it isn't DRM: the code still runs in this process. Your own tools installed back from the market stay plain `.js`.

**Toolbox form standard (user-mandated, applies to every tool):** clicking any non-`launch` tool opens a persistent page in the tab's toolbox (`openToolPage`): a `form()` web page if the tool has one, otherwise the standard form from `buildDynamicForm` — fed by the tool's `formSpec`, or generated client-side from `params` by `paramsToFields` (label = first clause of `.describe()` after stripping "true 时 / 可选" prefixes, ≤8 chars or ≤10 for checkboxes, else `KEY_LABELS[key]`, else the key; full description becomes the hover `title`; arrays become one-per-line textareas, unknown shapes JSON textareas). Layout: flex-wrap, each field sized to its content (selects to longest option, number inputs to digit count and growing as you type, labels never widen a field), `full` for long content only. Pages keep their state across tab switches, can be collapsed to a one-line summary, and run results go to the chat split below. The draft test-run form and the "＋ 新建工具" form use the same look. `TOOLBOX_PROMPT` tells the model these rules (short 2–4 char labels, explanations in `title`/`placeholder`, `chips` for ≤6 frequently switched options, related fields adjacent, output options not mixed into other sections, prefer the standard form over `form()` pages).

**claude process lifecycle (user rule: the process normally lives as long as its tab):** one `claude` process per tab (`Agent.q`), started early by `warm()` for the first tab, otherwise on the first message.
- **Clears and keeps the process** (`/clear` via `Agent.clear()`): 新对话, clicking a tool card in the toolbox, and editing the *first* message of the current conversation.
- **Restarts the process**, because the change can only happen at process start:
  - closing the tab;
  - login / logout or token expiry, because the relay token is in the process env;
  - a settings change to `apiKey` / `baseUrl` / `cwd`;
  - resuming a history session (`resume`);
  - editing a later message (truncation needs `resume` + `resumeSessionAt`);
  - 清空 history (otherwise the live process writes the transcript back);
  - entering making mode with ＋ 新建工具 or 编辑;
  - a crashed session;
  - `clear()` falling back to `reset()` when a reply won't stop within 5 s.
- **Why making mode restarts:** the system prompt is fixed when the process starts. Making mode appends `MAKING_PROMPT` (drafts only under `_drafts/`, recording, self-testing, hints), and `WECHAT_PROMPT` is only included when the tool is about 公众号 / 微信, to save tokens. So `startMaking()` calls `reset()` and the next `start()` builds the new prompt.
- **Making mode without a restart:** entering it from the chat (`toolbox_new` / `toolbox_edit`) and 继续修改 (`continueMaking()`) keep the process and the chat. `MAKING_PROMPT` arrives as the tool result instead, which the model may follow less reliably than a system prompt.
- **Possible change, discussed with the user but not done:** 新建工具 / 编辑 could use `/clear` plus `MAKING_PROMPT` as the first message. That saves the roughly 0.5 s process start.
- Model settings changes (`model`, `permissionMode`) and language changes don't restart either: `setModel` / `setPermissionMode` act on the live session, and a language change is prefixed to the next message.

**Clearing a chat keeps the claude process (`Agent.clear()`, user-requested):** clicking any tool card in the toolbox (`freshChatForTool`, a different tool or the one already open) and the 新对话 button (`clearChat`) call `agent:clear`. That empties the tab's chat DOM and pushes `/clear` into the live session's inbox, like typing /clear in the terminal: the native `claude` process keeps running, only the context is dropped, so the next message doesn't wait for a process start. The CLI answers with `conversation_reset` (`new_conversation_id`, which becomes `sessionId`, with `tagged = false` so the new transcript gets tagged after its first turn), a fresh `system init` and a `result`. `loop()` swallows everything except `system` messages while `this.clearing` is set, until that `result`. If the model is replying, `clear()` interrupts first and falls back to `reset()` only if it doesn't stop within 5 s. The process is closed only when the tab closes or a restart is unavoidable (login / logout, user API key or model settings change, entering making mode, resuming a history session, 清空 history, a crashed session). Verified: same PID before and after, and the model no longer knew a code word from before the clear. Model conversations stay in 历史; direct tool-run results are lost, which the user accepted. Tool cards don't clear while the model is replying, a tool is running or making mode is on.

**Pre-started claude process (`Agent.warm()`, user-requested):** 1.5 s after launch the first tab's agent runs `start()` in the background, so the first message doesn't wait for the `claude` process to boot. After a login, or a settings change that forces a restart (`apiKey` / `baseUrl` / `cwd`), the current tab warms again after 500 ms. A failure (logged out, quota used up) is silent; `send()` then reports it as before. `this.starting` holds the in-flight start: `send()`, `resume()`, `edit()` and `startMaking()` `settle()` it first, so two processes never start. `clear()` doesn't wait: with no process yet there's nothing to clear. `closeSession()` bumps `this.gen`, and `start()` gives up after its account check if the generation changed (tab closed, login changed). `clear()` does nothing on a warmed session that has had no message yet. Other tabs still start on their first message. Verified: the process exists before any message, and the same PID answers it. Measured gain is small: `init` arrives about 60 ms after the first message on a warmed tab versus about 500 ms on a cold one, while the first text took 4–9 s either way, which is model and relay latency.

**Editing a sent message (`Agent.edit(i, text)`, `editUserMsg` in `renderer.js`):** hovering a user message shows 修改 to its left. Sending the edit removes that message and everything below it from the DOM and calls `agent:edit`. `send()` records, for each turn, the last chain entry seen before it (`turns[i].at` = `lastChainUuid`, updated from every non-replay `assistant` / `user` message with a `uuid`), and the `user` event carries `turn` only when the message is editable. Messages the program sends with different shown text, messages sent in making mode, and the first turns after resuming a history session (chain tail unknown until a message arrives) are not editable. Editing the first turn of the current conversation runs `clear()` and resends, keeping the process. Editing a later turn needs truncation, which the SDK only does when a session opens, so `closeSession()` (no `reset` event) is followed by `start({resume: sessionId, resumeSessionAt: turn.at})` and the resend. This is the one case besides those listed above where the process restarts. A `reset` event removes every 修改 button in that tab, because the old turns are gone. **Auto-memory is rewound too:** Claude Code's auto-memory (`~/.claude/projects/<cwd with non-alphanumerics → ->/memory/`) is written with Write and with Bash `sed`/`echo >>`, so truncating the conversation alone left facts from the dropped turns (the user hit this: a fruit mentioned in an edited-away turn was still remembered). `send()` stores `memSnapshot()` (files up to 256 KB) on each editable turn, and `edit()` calls `memRestore()` before resending: files created later are deleted, changed or deleted ones are written back. The SDK's `rewindFiles` wasn't used because it only tracks Write/Edit. Both paths verified with a color and an animal saved to memory in the dropped turn. A memory written by another tab in the meantime is rolled back as well. Verified both paths: a code word set in an edited-away turn was forgotten, and the PID stayed the same when the first message was edited.

**Plugin repair: run profiling, error and slowness analysis (user-requested):** the user's goal is to have Claude analyze a plugin's code to find why it fails or runs very slowly. A plugin is its notes (`<name>.notes.md`, the intended steps) plus its code, and the analysis uses both.

How a run is profiled:
- `stoppableCtx(signal, meta, sess)` wraps every `ctx` method with `profOp()`. Each call is recorded with its category, its duration and its caller's location: the first stack frame inside the tool's directory, as `file:line`, including `_lib/*.mjs`. Categories: `sleep` 固定等待, `waitFor` 等页面条件, `navigate` 页面跳转, `js` 页面脚本/接口请求, click/type/press/scroll/upload 页面操作, `ask` 模型生成, everything else 其它操作.
- Nested calls, such as `ctx.js` inside a `waitFor` check, run under an `AsyncLocalStorage` flag and aren't counted twice.
- 插件自己的代码 = total − the sum of all categories. That's work that never touches `ctx`, like IMAP or local fetches.
- A `waitFor` whose duration reaches its timeout counts as 等满超时 even if it returned instead of throwing. Rejected ops are marked too.
- `ctx.log` and `ctx.warn` lines become step boundaries and carry `at` (ms since start). The renderer prefixes them with `+N.Ns`.
- Issues come from three places: `ctx.warn`, log lines matching `ISSUE_RE` (the `noteTestIssue` words plus their traditional-Chinese forms), and result lines starting with `⚠`. The thrown error is recorded unless it's a manual stop.
- Descriptions never include typed text or `js` code, which may contain passwords. URLs lose their query string.

Which runs are profiled:
- `runStoppable(def, args, meta)` covers toolbox runs, chat-invoked tools and scheduled runs; making-mode draft runs pass no `meta`.
- `form()` tools get a ctx whose `withSignal()` carries `meta`. Each form-page action is profiled as an idle-ended session: it ends 3 s after the last call, or the last log line if that comes later. `manulife_plan`'s 试算 is profiled this way; its background prefetch uses the raw ctx, so it isn't counted.

What is stored and shown:
- `profEnd()` returns `{name, title, file, notes, market, at, total, cats, steps, slow, typical, issues, error}`. `slow` holds up to 12 ops grouped by `where`+method, each with a count, total ms and how many timed out or failed. `typical` is the median of the previous ≥3 runs in `<userData>/tool-stats.json`, which keeps the last 10 per tool.
- The latest profile per tool goes to `<userData>/tool-profiles.json`, but only runs of at least 300 ms.
- A `tool_profile` event is emitted when total ≥ 3 s, or when there is an error or an issue. In a toolbox run or a scheduled run, the renderer holds it (`pendingProfile`, `tbRunning` / `schedHold`) and draws it under the result.
- `renderProfile()` shows a `<details>` line `⏱ 用时 … · categories`, opened when something went wrong, containing 报错, 警告, 分步耗时 and 最耗时的操作.
- The button depends on the outcome: error → 让 Claude 分析出错原因; issues → 让 Claude 检查这些问题; total ≥ 15 s → 让 Claude 分析为什么慢.
- **Repair means Claude analyzes *and modifies* the plugin's source (user-defined).** `startRepair()` enters making mode for the tool (`beginMaking({edit})`, which copies the code to `_drafts/<name>.js`) and sends `repairMsg()`. That message holds the run data (`profSections`: params, error, warnings, categories, steps, slow code lines), the notes path and the draft path. It asks Claude to find the real cause against the notes' steps and the code lines (checking the live page with `mcp__browser__*` for errors, no guessing), edit the draft to fix errors and cut waits without changing the tool's behavior, params or output, verify with `making_test`, and report the cause, the changes and the speed-up. The original is replaced only when the user clicks 保存工具; 不做了 leaves it untouched. `_lib/` is write-protected in making mode, so a cause inside a library is reported, not edited. Causes on the website's side are reported, not forced.
- Button labels: error → 让 Claude 修复错误; issues → 让 Claude 修复这些问题; total ≥ 15 s → 让 Claude 提速修复. A toolbox run that throws no longer shows the old 打开修改工具; the repair button below the error replaces it. Draft test-run failures keep 让助手诊断并修复.
- Market `.bxt` tools can't be edited, so they stay analysis-only (`profileMsg`, 让 Claude 分析… labels): no code locations, and Claude is told not to look for the source.
- Scheduled runs keep the profile on the history entry: `main.js` sets `task._profile`, and `scheduler.record()` moves it onto the entry. 执行情况 shows the categories and the same button.

**「工具运行完毕…」stays last (`keepLast` in `renderer.js`):** after a toolbox run, a `MutationObserver` on the tab's chat moves that note back to the bottom whenever something lands after it. Examples: a plugin injecting its own DOM later (`fff`'s 下載保單詳情 button, added in a `setTimeout`), download notes, the ⏱ profile. It stops once the user sends a message or a new run / schedule starts. It checks `d.parentNode === tab.el`, not `isConnected`, because a background tab's chat isn't attached to the document.

The 修复 button on every toolbox card (`repairTool`):
- It calls `tools:repairInfo` → `toolRepairInfo()`, then `startRepair()` with the latest saved profile.
- Without a profile, the repair message asks Claude to read the notes and the draft for likely failure points and slow waits, fix them, and test.
- A market tool with no run yet just gets a note: run it once first. The 执行情况 button also goes through `startRepair()`.

Verified with a temporary test tool through the toolbox UI in ok, warn and fail modes and through a scheduled run plus 执行情况, then removed. Two problems found and fixed while testing:
- `clear()` used to wait for a warming `start()`. A tool click right after launch therefore stalled, and the late clear wiped that run's output. `clear()` now returns at once when no process exists yet.
- `waitFor` timeouts weren't marked, which the duration check above now handles.

**Remembered tool credentials:** tool forms detect username / password fields with `credKind()` in `renderer.js`. It matches a formSpec field's `secret: 'username' | 'password'`, keys like username / password / pwd / login_id, or labels and descriptions starting with 登入名 / 账号 / 密码 …. Business fields such as 代理号 are not matched. Password fields render as `type=password`, and a 记住账号密码 checkbox (on by default) plus 清除已记住的 appear. Only those fields are stored, through `creds:get/set/clear` in `main.js`. They are encrypted with `safeStorage` into `<userData>/tool-creds.json` (mode 600), keyed by BrowserX account email (else `local`) and tool ID. Nothing is stored when encryption is unavailable. Saved values fill those fields on open unless the user edited the field in this tab (`tab.credTyped`). A value the tool itself supplies (a formSpec `value`, e.g. a test account the author left in a new version) does not block the fill, so a market overwrite install or update never hides the remembered login. Install and update only replace the tool's code file: `tool-creds.json`, the browser session (`persist:browser`) and files tools keep outside `tools/` (e.g. `<userData>/prudential_login.json`) are untouched; only deleting the tool clears its remembered credentials. Checking the box or running saves; unchecking or 清除 removes. Deleting the tool or logging out clears them. `maskArgs()` replaces passwords with `***` in diagnose messages, the making log and the schedule list.

**Dynamic tool forms (`formSpec`):** besides static `params` forms and `form()` web pages, a tool can export `formSpec(values, ctx)` (plain JS, runs in the main process, can use `ctx` to read the page, cached files, etc.) returning `{ fields, submit }`. Each field: `{ key, label, kind: enum|number|string|text|boolean|note|section|hidden, options:[{value,label}], value, refresh: true|'input', required, hint, full, min, max, step, tone }`. The renderer (`buildDynamicForm`) draws exactly what it returns; when a `refresh` field changes it calls `tools:formSpec` again with all current values and redraws, so dependent options, show/hide, computed defaults and chained rules all live in the tool. `hidden` fields carry state between calls. Values are kept per tab per tool (`tab.formValues`). Submit calls `run({...visibleValues, _form: true}, ctx)`. Like `form()` pages, dynamic forms open as a page that stays alive in the tab's toolbox (`openToolPage`), with the chat split below and the composer visible, so results land in the chat where the model can see them. `manulife_plan` (in `<userData>/tools/`, outside the repo) uses this; its old web form still opens in a separate window via `form:true`.

**Bookmarks:** the toolbar button that used to toggle the page DevTools now toggles a bookmarks bar under the URL bar (page DevTools moved to the menu: 显示 → 网页开发者工具, ⌥⌘I). Bookmarks are `<userData>/bookmarks.json` (`bookmarks:*` IPC in `main.js`), shared by all tabs; clicking one opens it in the current tab.

**`agent.js` is the core.** The `Agent` class wraps one `sdk.query()` session at a time (`this.q`), fed by a custom streaming `Inbox` (an async-iterable queue) so the conversation can stay open across multiple user turns without restarting the CLI process. Key things to know before touching it:

- **Tool groups are registered as separate in-process MCP servers**, all `alwaysLoad: true` (needed so they're not hidden behind tool search): `tools()` — generic browser control (`screenshot`, `page_info`, `navigate`, `click`, `type`, `press`, `scroll`, `eval`, `cdp`) driven by `executeJavaScript`/`sendInputEvent`/the Chrome DevTools Protocol against `this.wc` (the embedded view's `webContents`) — `wechatTools()` — the three WeChat actions (`wx_fill`, `wx_save_draft`, `wx_publish`), which delegate to `wechat.js`'s `WeChat` class — and `loadCustomTools()` (see next bullet). The five low-level browser actions are implemented once as `doNavigate`/`doClick`/`doType`/`doPress`/`doScroll` methods on `Agent`; both the `tools()` definitions and custom tools' `ctx` call the same implementation, so permission/`guard()` behavior never diverges between the two.
- **Toolbox (custom tools)**: users/the model can drop a `.js` file into `getToolsDir()` (`<userData>/tools/`, passed in from `main.js`) exporting `(z) => ({name, description, params, async run(args, ctx)})`; `loadCustomTools()` scans that directory on every `start()` (clearing `require.cache` first, so edits take effect on the next new conversation), validates the name against a collision list of built-in tool names, and registers each as a real MCP tool under the `custom` server. `ctx` exposes the same primitives as the built-in tools (`js`, `click`, `type`, `press`, `scroll`, `navigate`, `sleep`, `waitFor` — aliased to `wechat.js`'s generic polling helper — `guard`, `wc`, `wx`, `log`) so a custom tool can implement a real, branching, retry-aware procedure (the same style as `WeChat.fill()`) instead of a brittle flat click-replay. This exists specifically so a manually-verified or already-documented flow (e.g. a Claude Code skill) can be "compiled" into a fast, parameterized, directly-callable tool instead of re-deriving it step by step every conversation. `TOOLBOX_PROMPT` (in `agent.js`) is the exact contract communicated to the model — including the warning to avoid `z.record`/nested-object shapes in `params` (same SDK limitation that made `wx_fill`'s `images` and `cdp`'s `params` JSON-string-encoded instead of plain objects: a `z.record`-shaped param breaks registration for the *whole* tool group on the current SDK version). When a custom tool throws, the error text returned to the model includes the tool's own source file path plus an instruction to finish the task manually with `mcp__browser__*`, diagnose the real cause via the DOM (not guesswork), and patch that file directly — this is prompt-level guidance, not a code-level retry loop; there's no automatic self-healing, the model just has to be told to do it and where the file is.
- `readCustomToolDefs()` is the shared load+validate step (used by all three of the below); it's factored out so listing/running a tool never needs a live `sdk` object. `loadCustomTools(sdk)` wraps each into an SDK `tool()` for the chat/model path. `listCustomTools()` additionally introspects each `params` zod shape (this SDK's zod is v4: walk `schema._def.type` — `'optional'` unwraps via `._def.innerType`, `'array'` element type via `._def.element`, `'enum'` values via `._def.entries`; `schema.description` reads correctly regardless of `.describe()`/`.optional()` call order) into `{key, required, kind, enumValues?, description}` so the renderer can build a form without knowing anything about zod. `runCustomTool(name, args)` calls `def.run(args, this.toolCtx)` directly — same `ctx` as the chat path, so `guard()` confirmations and `log()` progress notes work identically — with **no model involved and no `sdk.query()` session created**, guarded by a `this._toolRunning` flag against overlapping runs. The "工具箱" sidebar panel (`index.html`/`style.css`/`renderer.js`, mirroring the existing "历史" panel's `#history`/`#h_list`/`renderHistoryList()` pattern) calls `tools:list`/`tools:run` (added in `main.js` next to the `history:*` handlers) to list tools, build a per-tool form from the introspected `params`, and run one directly — this is the "spend zero tokens" path the chat-driven `mcp__custom__*` calls don't give you. When a direct run throws, the error note in `#msgs` gets an inline "让 Claude 诊断并修复" button (`renderer.js`) that composes a message (tool name, args, error) into `#input` and calls `sendMsg()` — i.e. it hands the failure to the *other* (token-costing) path on demand, rather than trying to auto-fix without a model in the loop. `toolCtx` also exposes `article: { textToArticle, renderBlocks, THEMES }` (the same `./article` helpers `wx_fill` uses) alongside `wx`, so a custom tool can drive a full WeChat publish (fill + save-draft/publish) by composing already-proven code instead of reinventing it — see `example-tools/wechat_publish.js`. That directory is a **reference copy only** — the live, loaded-at-`start()` copy is whatever's in `getToolsDir()` (`<userData>/tools/`, outside the repo); nothing under `example-tools/` is read at runtime, it's there so tools survive a fresh `userData` and so future edits have a known-good example to crib from.
- **Tool-making mode** (`startMaking`/`runDraft`/`finishMaking`/`cancelMaking` in `agent.js`, banner `#makingBar` in the UI): "＋ 新建工具" (or a tool's "编辑") clears the chat, starts a dedicated conversation whose system prompt gets `MAKING_PROMPT`, and auto-sends a kickoff message. The model writes only to `<tools>/_drafts/<name>.js` (for an edit, the existing file is copied there first); `readCustomToolDefs` only scans the top level of `tools/`, so drafts never appear in the toolbox or get registered. "试运行" runs the draft directly (no model) and sets `tested`. "完成" validates the draft: it must load, its `name` must match, and no param may be `record`/nested `object` (that breaks registration of the whole `custom` group). It then asks for confirmation if the draft was never test-run or would overwrite another tool, moves the draft into `tools/`, and hot-reloads tools into the live session via `reloadCustomTools()`. The model no longer maintains `<name>.notes.md` during making: after the move, `writeNotes()` runs in the background (one `askModel()` call over the final code + `.process.md` + the old notes), overwrites the notes and only then emits the "运行步骤小结" note. `MAKING_PROMPT` also tells the model to use `making_hint` only when the user has to act (not for progress), not to re-ask what the user already stated, and to batch page inspection into few `eval` calls; each of those was a full model turn. **`setMcpServers` ignores a same-name replacement** (it returns empty `added`/`removed`), so the reload drops `custom` in one call and re-adds it in a second. "放弃" deletes the draft. The model can also enter making mode *without clearing the chat* via the `toolbox` MCP group (`toolbox_new` / `toolbox_edit`, which call `startMaking({keepChat:true})` and return `MAKING_PROMPT` as the tool result, since the session's system prompt predates the mode). The "继续修改" button on the `tool_done` note does the same through `continueMaking()`. **Official tool files are write-protected** by a `PreToolUse` hook (`protectToolFiles`). It denies Edit/Write/MultiEdit/NotebookEdit to `tools/` outside `_drafts/`, plus Bash commands that redirect into such a file or combine a write-ish command with such a path. A hook is used rather than `canUseTool` because in `bypassPermissions` mode `canUseTool` is never called, while hooks always run (verified in a real session). The Bash check is a heuristic, so a constructed path can still get past it. Making state lives only in memory: it survives "新对话" but not an app restart. A leftover draft is resumed when a tool of the same name is started again. **Smoother making flow:** 新建工具 is now a single question ("想做个什么工具？", with example chips). The name and title are generated: the banner shows 新工具 until the draft's `title` arrives through `checkDraftHook`. The goal is sent as the first chat message (`beginMaking`), with no prefill. The model tests the draft itself with `mcp__toolbox__making_test` (`makingTest()` → `runDraft`), up to 3 fix rounds, and asks first for tools that submit, pay, delete or publish. A pass emits `making_tested`, which renders a card with 保存到工具箱 and 换个参数试试. The banner shows progress (`MAKING_STEPS`, advanced by `makingStep()` from the model's tool calls: navigate → rec_start → draft Write/Edit → making_test → pass, never backwards; 看你示范 shows as skipped without a recording). Buttons are now 保存 (`SAVE_LABEL`) and 不做了, since the round banner buttons can't fit long labels. Smoothness rules: `MAKING_PROMPT` tells the model to reuse an existing skill, tool or notes first. While exploring it must never press the final submit / publish / save button, leaving that to `making_test`. It must send a `making_hint` whenever the user has to act, and it must not swallow a failing step: the step should return a `⚠ …` line or call `ctx.warn`. `makingTest` collects warnings in `_testIssues`, from `ctx.warn` and from `ctx.log` lines that look like failures, plus result lines starting with `⚠`. If there are any, it reports "有问题，不算通过" and doesn't emit `making_tested`. Reminders: when a turn ends, the program sets an action hint, either 测试通过 → 保存 or, if the model ended with a question, 助手在等你回答. While recording, `watchRecIdle()` nudges once per pause: 20 s after the user's last page input, or after 60 s with no input. An action hint suppresses the 要录制吗 prompt and, when the window is unfocused, triggers a system notification (`renderMaking`). 开始制作 is guarded against double clicks. While making, the model may start recording itself (`rec_start`); the banner hint is set by the program. Recording ends either when the user clicks 停止录制 (`making:recStop`) or when the user sends any chat message while recording (`userSend`). Both paths go through `finishMakingRec()`, which stops the recorder, sends the user's text plus the trace path to the model, and then emits `rec_result` so the result card shows below the user's message. The model doesn't need its own `rec_stop` turn. `modal()` hides the native view while open (`view:cover` IPC), because a centered DOM modal would otherwise sit behind it.
- **Network recording (`recorder.js`)**: `rec_start` / `rec_mark` / `rec_stop` (in the `browser` tool group, also exposed as `rec:*` IPC for a future UI button) record the embedded view's XHR/fetch/navigation traffic via the `Network` CDP domain on the *same* `wc.debugger` that `cdp()` uses, so the user can perform a flow by hand and the model can then turn the captured API calls into a custom tool that `fetch`es from inside the logged-in page (the approach used by `security-plan-maker`). Traces go to `<userData>/recon/<host>/trace-*.json`, outside the repo. Sensitive headers, cookies, and password/token-like body or URL fields are masked *before* writing. Before masking, each long secret is traced back to where it first appeared (a response field, a `localStorage` key, or a cookie) and listed in `tokenSources`, so a tool can be written to obtain the token without the trace ever containing it. Raw bodies live only in memory during recording. An in-progress recording is saved on `before-quit` and on debugger detach (e.g. the user opened DevTools).
- **Coordinates are always "screenshot coordinates"** (CSS pixels × a downscale factor `s` capped by `MAX_EDGE`/`MAX_PIXELS`, computed in `viewport()`), never raw CSS or device pixels. Every tool that takes x/y converts through `viewport()` before sending native input events (which need CSS px × zoom, not screenshot px).
- **Permissions**: `canUseTool()` auto-allows any `mcp__browser__*` call (those self-guard instead, see next point) and otherwise routes everything else through `ask()`/`permit()`, which round-trips to the renderer as a `permission` event and blocks on a `Map` of pending promises keyed by an incrementing id. `mcp__wechat__publish` is always asked individually (`warn: true`, no "always allow this session"), since it's irreversible.
- **AskUserQuestion** is answered through a `PreToolUse` hook (`questionHook`), not `canUseTool`, because in `bypassPermissions` mode `canUseTool` is never called. The hook emits a `question` event; the renderer draws a clickable card (`questionCard`), and `agent:answer` resolves it. The hook then allows the call with `updatedInput.answers` (question text → selected labels joined by `, `, with "其他" free text appended). Skipping, stopping or resetting denies the call with a "user skipped" reason. The matcher timeout is set to one day, because the default timeout would treat a slow answer as no answer. This was verified end-to-end in a real session.
- **`guard()`** is the other permission layer: browser tools that are about to click/submit/eval something call `guard(what, text)`, which only actually prompts when `permissionMode === 'default'` *and* the target text matches `DANGER` (删除/支付/购买/发表/publish/etc.). In every other permission mode it's a no-op — the coarser mode-level gate already decided.
- **`mutate()`** serializes page-mutating tool calls through `this.lock` so concurrent tool calls (rare, but the model can pipeline) don't click on top of each other.
- **History / sessions**: session transcripts are the *native* `claude` CLI's own storage under `~/.claude/projects/<cwd>/`, the same pool the terminal `claude`/`claude --resume` use. Because that pool isn't scoped to this app, every session BrowserX creates gets tagged `CB_TAG = 'claude-browser'` (via `sdk.tagSession`, called from `tagAndPrune()` right after each session's *first* completed turn — earlier than that and the native process hasn't finished writing the transcript file yet, so tagging fails). History keeps at most `HISTORY_MAX` (30) sessions, newest first. `pruneHistory()` also runs when the 历史 panel opens. 清空 (`history:clear` → `clearHistory()`) deletes every tagged session, including open ones: it refuses while a chat is replying, a tool is running or making mode is on, resets every tab's session first (otherwise the live `claude` process writes the file back), then moves the session files to the macOS Trash (`shell.trashItem`) instead of deleting them, so a mistaken clear can be undone. `listHistory()`/`pruneHistory()` only ever look at sessions carrying that tag, so a rename of `CB_TAG` orphans (hides, doesn't delete) every session created before the rename. `deleteHistory()` retries the delete a few times with a short wait and re-checks `listSessions()`, because a session whose native process was just closed can still be mid-write and resurrect the file it just deleted.

**`wechat.js`** drives the actual `mp.weixin.qq.com` editor: login-by-QR-wait (`ensureLogin`), then fills the ProseMirror body by writing HTML/an image to the OS clipboard and dispatching a native paste (`pasteHtml`/`pasteImage`) rather than typing — WeChat's editor doesn't take plain `insertText` reliably for rich content. `article.js` turns the model's constrained Markdown-like syntax (`## heading`, `- bullet`, `` ``` `` example, `> tip`, `![img] prompt`) into that HTML, styled by one of the `THEMES` (inline CSS only — the target is WeChat's editor, which strips `<style>`/external CSS).

**Renderer state to know about**: `renderer.js` keeps the whole chat as DOM (`#msgs`), not a JS model — history replay (`renderHistoryEvents`) just re-emits the same `add()`/`toolCard()`/`toolResult()` calls a live session would. The little `modal()`/`askText()`/`askConfirm()` helpers exist because Electron's renderer doesn't support `window.prompt()` and `window.confirm()` isn't reliable there.
