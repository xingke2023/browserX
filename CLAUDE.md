# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BrowserX (npm package `browserx`, formerly "Claude Browser") is an Electron desktop app: a Claude Code chat pane on the left, a real embedded browser on the right, which the agent controls directly (screenshots, clicks, JS eval, CDP) via the `@anthropic-ai/claude-agent-sdk`. It also ships a purpose-built tool set for publishing articles to WeChat Official Accounts (公众号) through that same browser view.

## Commands

```
npm start            # run the app (electron .)
npm run debug         # run with CB_DEBUG_PORT=9334 (adds --remote-debugging-port, useful for driving the renderer over CDP from outside)
CSC_IDENTITY_AUTO_DISCOVERY=false npx electron-builder --mac   # → dist/BrowserX-<version>-arm64.dmg (no npm script wraps this)
```

There is no lint config and no test suite in this package.

**Packaging notes:**
- The app is *not* signed with a Developer ID: `mac.identity` is `null`, and `scripts/after-pack.js` ad-hoc signs the bundled `claude` binary and then the whole `.app`. electron-builder treats identity `"-"` as a name lookup, skips signing, and leaves a broken signature, so `"-"` must not be used.
- `CSC_IDENTITY_AUTO_DISCOVERY=false` stops the build from picking up a company certificate that happens to be in the keychain.
- electron-builder nests the platform package under `claude-agent-sdk/node_modules/`. The `asarUnpack` glob therefore has to be `**/node_modules/@anthropic-ai/claude-agent-sdk-*/**`, and `nativeClaude()` checks both the top-level and the nested location.
- The build needs about 1.3 GB of free disk space at peak.

## Architecture

**Process split (standard Electron, but with a twist):** `main.js` creates one `BrowserWindow` (the whole UI, `index.html`/`renderer.js`) and layers `WebContentsView`s into it — those views *are* the right-hand "browser". `renderer.js` never touches a view directly; it only resizes them by sending the DOM position of `#stage` through the `bounds` IPC call so the native views line up under the DOM layout. `preload.js` exposes exactly two bridge calls: `api.call(channel, ...args)` → `ipcRenderer.invoke` and `api.on(channel, fn)`.

**Tabs (left tab = right view = one `Agent`, strictly 1:1):** `main.js` keeps `tabs` (`Map<id, {view, agent, navError}>`) and `cur`; `createTab()` builds a view plus its own `Agent`, so every agent, `WeChat`, `Recorder` and custom-tool `ctx` is bound to its own tab's `webContents`, and a background tab's agent never touches the visible page. Only the tab bar on the left exists (no browser-style tab strip on the right); `target=_blank` still opens in the same view, so there are never tabs without a chat. Inactive views are hidden with `setVisible(false)` and created with `backgroundThrottling: false` — verified that a hidden view still returns fresh `capturePage()` images, runs timers and accepts `sendInputEvent`, so background agents work normally. All views get the same bounds (a 0-size `bounds` call while dragging the splitter only hides the current one). Agent events are sent as `{...ev, tab: id}`; IPC calls that act on a conversation (`agent:*`, `tools:run`/`tools:stop`, `history:resume`) take a trailing tab id, falling back to `cur`. Nav, recording buttons, history list and toolbox listing act on `cur`. Tool-making mode is limited to one tab at a time (`ctx.otherMaking`), and `making:*` banner calls go to that tab; after a tool is finished or imported, `ctx.toolsChanged` reloads custom tools in the other tabs' live sessions. `wechat.js` serializes clipboard-write + paste through a module-level `clipLock`, since the OS clipboard is shared. In `renderer.js` each tab has its own state object (`tabState`: message container, card maps, running, making…); the visible container gets `id="msgs"` (all chat CSS targets `#msgs`). `cur` is the shown tab and `T` the tab being rendered into — events from a background tab and async tool results use `inTab()` to temporarily point `T` (and therefore `add()`) at their own tab. Resuming a history session that is already open switches to that tab; otherwise it opens in a new tab unless the current one is empty. Shortcuts ⌘T / ⌘W / ⌘1…9 / ⌘⇧[ ] are also caught via each view's `before-input-event` and forwarded as `tabkey`, so they work while focus is in the web page. Max 8 tabs.

**BrowserX account (`account.js`, portal `browserx.xingke888.com` = `~/github/browserx-portal`):** login is a loopback + PKCE flow — `Account.login()` listens on a random `127.0.0.1` port, opens `<portal>/desktop/authorize?port&state&challenge&device` in the *system* browser (`shell.openExternal`), and on `/callback?code&state` exchanges `code + verifier` at `POST /api/desktop/token` for a Sanctum token; callbacks with the wrong `state` are ignored, the wait times out after 10 minutes, `account:cancel` aborts it. The token lives in `main.js`'s `accountToken`, **not** in `cfg` (cfg is sent whole to the renderer), and is written to `config.json` as `accountTokenEnc` only when `safeStorage` encryption is available. All other calls go to `/api/desktop/*` with `Bearer`; a 401 clears the token (logged out), 402/403 errors carry the site `url` (buy / become a member) which `handle()` passes through as `{error, url, needLogin}` so the renderer can show a "去网站看看" button (`.ac_link` → `account:open`, which only opens URLs on the portal). Market install = download code (`/market/{id}/download`) to a temp file, then the **same** `importPreview` → user confirm → `tools:importConfirm` path as a local import; successful market installs are recorded in `<userData>/market-installed.json` (name → id/version/sha256) for the "已安装 / 有新版本" labels. Publish (`market:publishInfo` / `market:publish`) posts the toolbox file plus form fields; the portal decides new tool vs. new version by the file's `name`, and everything goes to admin review. `CB_PORTAL` points at another portal (local testing) and `CB_ACCOUNT_TOKEN` injects a token without the browser step — test-only, like `CB_USER_DATA`.

**Market tool protection:** tools installed from the market that belong to someone else (`market-installed.json` entry without `mine`; the portal's download response says `mine`) are stored encrypted as `<tools>/<name>.bxt` (`toolcrypt.js`: AES-256-GCM, random key per tool, tool name as AAD, keys in `<userData>/tool-keys.json` encrypted with `safeStorage`). `loadToolFile` decrypts and compiles them in memory via `Module#_compile`, so no plaintext touches disk; `readCustomToolDefs` lists `.bxt` alongside `.js`. They can't be edited / exported / published (`isMarketTool` + a `.bxt` check in `startMaking` / `exportInfo`; the UI hides those buttons and shows a "市场" chip), their failure message tells the model not to look for the source, deleting one also drops its key, and on startup `encryptMarketTools()` converts older plaintext market installs (deleting the `.js` only after a decrypt round-trip matches). This raises the bar, it isn't DRM: the code still runs in this process. Your own tools installed back from the market stay plain `.js`.

**Toolbox form standard (user-mandated, applies to every tool):** clicking any non-`launch` tool opens a persistent page in the tab's toolbox (`openToolPage`): a `form()` web page if the tool has one, otherwise the standard form from `buildDynamicForm` — fed by the tool's `formSpec`, or generated client-side from `params` by `paramsToFields` (label = first clause of `.describe()` after stripping "true 时 / 可选" prefixes, ≤8 chars or ≤10 for checkboxes, else `KEY_LABELS[key]`, else the key; full description becomes the hover `title`; arrays become one-per-line textareas, unknown shapes JSON textareas). Layout: flex-wrap, each field sized to its content (selects to longest option, number inputs to digit count and growing as you type, labels never widen a field), `full` for long content only. Pages keep their state across tab switches, can be collapsed to a one-line summary, and run results go to the chat split below. The draft test-run form and the "＋ 新建工具" form use the same look. `TOOLBOX_PROMPT` tells the model these rules (short 2–4 char labels, explanations in `title`/`placeholder`, `chips` for ≤6 frequently switched options, related fields adjacent, output options not mixed into other sections, prefer the standard form over `form()` pages).

**Dynamic tool forms (`formSpec`):** besides static `params` forms and `form()` web pages, a tool can export `formSpec(values, ctx)` (plain JS, runs in the main process, can use `ctx` to read the page, cached files, etc.) returning `{ fields, submit }`. Each field: `{ key, label, kind: enum|number|string|text|boolean|note|section|hidden, options:[{value,label}], value, refresh: true|'input', required, hint, full, min, max, step, tone }`. The renderer (`buildDynamicForm`) draws exactly what it returns; when a `refresh` field changes it calls `tools:formSpec` again with all current values and redraws, so dependent options, show/hide, computed defaults and chained rules all live in the tool. `hidden` fields carry state between calls. Values are kept per tab per tool (`tab.formValues`). Submit calls `run({...visibleValues, _form: true}, ctx)`. Like `form()` pages, dynamic forms open as a page that stays alive in the tab's toolbox (`openToolPage`), with the chat split below and the composer visible, so results land in the chat where the model can see them. `manulife_plan` (in `<userData>/tools/`, outside the repo) uses this; its old web form still opens in a separate window via `form:true`.

**Bookmarks:** the toolbar button that used to toggle the page DevTools now toggles a bookmarks bar under the URL bar (page DevTools moved to the menu: 显示 → 网页开发者工具, ⌥⌘I). Bookmarks are `<userData>/bookmarks.json` (`bookmarks:*` IPC in `main.js`), shared by all tabs; clicking one opens it in the current tab.

**`agent.js` is the core.** The `Agent` class wraps one `sdk.query()` session at a time (`this.q`), fed by a custom streaming `Inbox` (an async-iterable queue) so the conversation can stay open across multiple user turns without restarting the CLI process. Key things to know before touching it:

- **Tool groups are registered as separate in-process MCP servers**, all `alwaysLoad: true` (needed so they're not hidden behind tool search): `tools()` — generic browser control (`screenshot`, `page_info`, `navigate`, `click`, `type`, `press`, `scroll`, `eval`, `cdp`) driven by `executeJavaScript`/`sendInputEvent`/the Chrome DevTools Protocol against `this.wc` (the embedded view's `webContents`) — `wechatTools()` — the three WeChat actions (`wx_fill`, `wx_save_draft`, `wx_publish`), which delegate to `wechat.js`'s `WeChat` class — and `loadCustomTools()` (see next bullet). The five low-level browser actions are implemented once as `doNavigate`/`doClick`/`doType`/`doPress`/`doScroll` methods on `Agent`; both the `tools()` definitions and custom tools' `ctx` call the same implementation, so permission/`guard()` behavior never diverges between the two.
- **Toolbox (custom tools)**: users/the model can drop a `.js` file into `getToolsDir()` (`<userData>/tools/`, passed in from `main.js`) exporting `(z) => ({name, description, params, async run(args, ctx)})`; `loadCustomTools()` scans that directory on every `start()` (clearing `require.cache` first, so edits take effect on the next new conversation), validates the name against a collision list of built-in tool names, and registers each as a real MCP tool under the `custom` server. `ctx` exposes the same primitives as the built-in tools (`js`, `click`, `type`, `press`, `scroll`, `navigate`, `sleep`, `waitFor` — aliased to `wechat.js`'s generic polling helper — `guard`, `wc`, `wx`, `log`) so a custom tool can implement a real, branching, retry-aware procedure (the same style as `WeChat.fill()`) instead of a brittle flat click-replay. This exists specifically so a manually-verified or already-documented flow (e.g. a Claude Code skill) can be "compiled" into a fast, parameterized, directly-callable tool instead of re-deriving it step by step every conversation. `TOOLBOX_PROMPT` (in `agent.js`) is the exact contract communicated to the model — including the warning to avoid `z.record`/nested-object shapes in `params` (same SDK limitation that made `wx_fill`'s `images` and `cdp`'s `params` JSON-string-encoded instead of plain objects: a `z.record`-shaped param breaks registration for the *whole* tool group on the current SDK version). When a custom tool throws, the error text returned to the model includes the tool's own source file path plus an instruction to finish the task manually with `mcp__browser__*`, diagnose the real cause via the DOM (not guesswork), and patch that file directly — this is prompt-level guidance, not a code-level retry loop; there's no automatic self-healing, the model just has to be told to do it and where the file is.
- `readCustomToolDefs()` is the shared load+validate step (used by all three of the below); it's factored out so listing/running a tool never needs a live `sdk` object. `loadCustomTools(sdk)` wraps each into an SDK `tool()` for the chat/model path. `listCustomTools()` additionally introspects each `params` zod shape (this SDK's zod is v4: walk `schema._def.type` — `'optional'` unwraps via `._def.innerType`, `'array'` element type via `._def.element`, `'enum'` values via `._def.entries`; `schema.description` reads correctly regardless of `.describe()`/`.optional()` call order) into `{key, required, kind, enumValues?, description}` so the renderer can build a form without knowing anything about zod. `runCustomTool(name, args)` calls `def.run(args, this.toolCtx)` directly — same `ctx` as the chat path, so `guard()` confirmations and `log()` progress notes work identically — with **no model involved and no `sdk.query()` session created**, guarded by a `this._toolRunning` flag against overlapping runs. The "工具箱" sidebar panel (`index.html`/`style.css`/`renderer.js`, mirroring the existing "历史" panel's `#history`/`#h_list`/`renderHistoryList()` pattern) calls `tools:list`/`tools:run` (added in `main.js` next to the `history:*` handlers) to list tools, build a per-tool form from the introspected `params`, and run one directly — this is the "spend zero tokens" path the chat-driven `mcp__custom__*` calls don't give you. When a direct run throws, the error note in `#msgs` gets an inline "让 Claude 诊断并修复" button (`renderer.js`) that composes a message (tool name, args, error) into `#input` and calls `sendMsg()` — i.e. it hands the failure to the *other* (token-costing) path on demand, rather than trying to auto-fix without a model in the loop. `toolCtx` also exposes `article: { textToArticle, renderBlocks, THEMES }` (the same `./article` helpers `wx_fill` uses) alongside `wx`, so a custom tool can drive a full WeChat publish (fill + save-draft/publish) by composing already-proven code instead of reinventing it — see `example-tools/wechat_publish.js`. That directory is a **reference copy only** — the live, loaded-at-`start()` copy is whatever's in `getToolsDir()` (`<userData>/tools/`, outside the repo); nothing under `example-tools/` is read at runtime, it's there so tools survive a fresh `userData` and so future edits have a known-good example to crib from.
- **Tool-making mode** (`startMaking`/`runDraft`/`finishMaking`/`cancelMaking` in `agent.js`, banner `#makingBar` in the UI): "＋ 新建工具" (or a tool's "编辑") clears the chat, starts a dedicated conversation whose system prompt gets `MAKING_PROMPT`, and auto-sends a kickoff message. The model writes only to `<tools>/_drafts/<name>.js` (for an edit, the existing file is copied there first); `readCustomToolDefs` only scans the top level of `tools/`, so drafts never appear in the toolbox or get registered. "试运行" runs the draft directly (no model) and sets `tested`. "完成" validates the draft: it must load, its `name` must match, and no param may be `record`/nested `object` (that breaks registration of the whole `custom` group). It then asks for confirmation if the draft was never test-run or would overwrite another tool, moves the draft into `tools/`, and hot-reloads tools into the live session via `reloadCustomTools()`. **`setMcpServers` ignores a same-name replacement** (it returns empty `added`/`removed`), so the reload drops `custom` in one call and re-adds it in a second. "放弃" deletes the draft. The model can also enter making mode *without clearing the chat* via the `toolbox` MCP group (`toolbox_new` / `toolbox_edit`, which call `startMaking({keepChat:true})` and return `MAKING_PROMPT` as the tool result, since the session's system prompt predates the mode). The "继续修改" button on the `tool_done` note does the same through `continueMaking()`. **Official tool files are write-protected** by a `PreToolUse` hook (`protectToolFiles`). It denies Edit/Write/MultiEdit/NotebookEdit to `tools/` outside `_drafts/`, plus Bash commands that redirect into such a file or combine a write-ish command with such a path. A hook is used rather than `canUseTool` because in `bypassPermissions` mode `canUseTool` is never called, while hooks always run (verified in a real session). The Bash check is a heuristic, so a constructed path can still get past it. Making state lives only in memory: it survives "新对话" but not an app restart. A leftover draft is resumed when a tool of the same name is started again. `modal()` hides the native view while open (`view:cover` IPC), because a centered DOM modal would otherwise sit behind it.
- **Network recording (`recorder.js`)**: `rec_start` / `rec_mark` / `rec_stop` (in the `browser` tool group, also exposed as `rec:*` IPC for a future UI button) record the embedded view's XHR/fetch/navigation traffic via the `Network` CDP domain on the *same* `wc.debugger` that `cdp()` uses, so the user can perform a flow by hand and the model can then turn the captured API calls into a custom tool that `fetch`es from inside the logged-in page (the approach used by `security-plan-maker`). Traces go to `<userData>/recon/<host>/trace-*.json`, outside the repo. Sensitive headers, cookies, and password/token-like body or URL fields are masked *before* writing. Before masking, each long secret is traced back to where it first appeared (a response field, a `localStorage` key, or a cookie) and listed in `tokenSources`, so a tool can be written to obtain the token without the trace ever containing it. Raw bodies live only in memory during recording. An in-progress recording is saved on `before-quit` and on debugger detach (e.g. the user opened DevTools).
- **Coordinates are always "screenshot coordinates"** (CSS pixels × a downscale factor `s` capped by `MAX_EDGE`/`MAX_PIXELS`, computed in `viewport()`), never raw CSS or device pixels. Every tool that takes x/y converts through `viewport()` before sending native input events (which need CSS px × zoom, not screenshot px).
- **Permissions**: `canUseTool()` auto-allows any `mcp__browser__*` call (those self-guard instead, see next point) and otherwise routes everything else through `ask()`/`permit()`, which round-trips to the renderer as a `permission` event and blocks on a `Map` of pending promises keyed by an incrementing id. `mcp__wechat__publish` is always asked individually (`warn: true`, no "always allow this session"), since it's irreversible.
- **AskUserQuestion** is answered through a `PreToolUse` hook (`questionHook`), not `canUseTool`, because in `bypassPermissions` mode `canUseTool` is never called. The hook emits a `question` event; the renderer draws a clickable card (`questionCard`), and `agent:answer` resolves it. The hook then allows the call with `updatedInput.answers` (question text → selected labels joined by `, `, with "其他" free text appended). Skipping, stopping or resetting denies the call with a "user skipped" reason. The matcher timeout is set to one day, because the default timeout would treat a slow answer as no answer. This was verified end-to-end in a real session.
- **`guard()`** is the other permission layer: browser tools that are about to click/submit/eval something call `guard(what, text)`, which only actually prompts when `permissionMode === 'default'` *and* the target text matches `DANGER` (删除/支付/购买/发表/publish/etc.). In every other permission mode it's a no-op — the coarser mode-level gate already decided.
- **`mutate()`** serializes page-mutating tool calls through `this.lock` so concurrent tool calls (rare, but the model can pipeline) don't click on top of each other.
- **History / sessions**: session transcripts are the *native* `claude` CLI's own storage under `~/.claude/projects/<cwd>/`, the same pool the terminal `claude`/`claude --resume` use. Because that pool isn't scoped to this app, every session BrowserX creates gets tagged `CB_TAG = 'claude-browser'` (via `sdk.tagSession`, called from `tagAndPrune()` right after each session's *first* completed turn — earlier than that and the native process hasn't finished writing the transcript file yet, so tagging fails). `listHistory()`/`pruneHistory()` only ever look at sessions carrying that tag, so a rename of `CB_TAG` orphans (hides, doesn't delete) every session created before the rename. `deleteHistory()` retries the delete a few times with a short wait and re-checks `listSessions()`, because a session whose native process was just closed can still be mid-write and resurrect the file it just deleted.

**`wechat.js`** drives the actual `mp.weixin.qq.com` editor: login-by-QR-wait (`ensureLogin`), then fills the ProseMirror body by writing HTML/an image to the OS clipboard and dispatching a native paste (`pasteHtml`/`pasteImage`) rather than typing — WeChat's editor doesn't take plain `insertText` reliably for rich content. `article.js` turns the model's constrained Markdown-like syntax (`## heading`, `- bullet`, `` ``` `` example, `> tip`, `![img] prompt`) into that HTML, styled by one of the `THEMES` (inline CSS only — the target is WeChat's editor, which strips `<style>`/external CSS).

**Renderer state to know about**: `renderer.js` keeps the whole chat as DOM (`#msgs`), not a JS model — history replay (`renderHistoryEvents`) just re-emits the same `add()`/`toolCard()`/`toolResult()` calls a live session would. The little `modal()`/`askText()`/`askConfirm()` helpers exist because Electron's renderer doesn't support `window.prompt()` and `window.confirm()` isn't reliable there.
